Sin herramientas, el modelo solo puede rendirse o inventarse la respuesta. En 6 días de 30 minutos, más el día 0 de preparación, le damos manos. Y después las blindamos, porque una demo que funciona el martes y se cae el sábado a las 3 de la mañana no le sirve a nadie.

Un día es una sentada, y termina con algo corriendo en tu máquina. No te leas el taller entero de una: haz un día, ciérralo, y vuelve mañana. Lo digo en serio, aunque te sientas con cuerda para seguir. Esto se aprende durmiendo entre sesión y sesión.

Cada paso trae el código completo (botón Copiar), el comando para correrlo y la salida real que deberías ver. Esa salida es tu criterio de "me funcionó": si lo tuyo se parece, sigue; si no, ahí tienes por dónde empezar a mirar, y no necesitas preguntarme.

El taller tiene dos actos. Los días 1 a 4 son haz que funcione: el modelo pide, tu código ejecuta. Los días 5 y 6 son haz que sobreviva: lo mismo, pero aguantando errores de red, rate limits y timeouts.

Marca cada paso conforme lo termines, con el círculo de la izquierda o con el botón del final: tu progreso queda guardado en este navegador, así que puedes cerrar y volver mañana sin perder el hilo. Atajos: j / k para saltar entre pasos, w para ajustar líneas, c para las notas del coach.

Una última cosa antes de empezar. Si algo no te cuadra, no sigas adelante esperando que se aclare solo: casi nunca pasa. Anótalo y lo vemos.

La historia de esta sesión

Sin herramientas, un modelo solo tiene dos salidas ante algo que no sabe: rendirse o inventárselo. Dándole herramientas cambia de categoría: pasa de escribir texto a hacer cosas.

Y ahí aparece el problema nuevo, que es el que de verdad te va a ocupar tiempo. En cuanto tu código llama a un servicio real, hereda todo lo que les pasa a los servicios reales: se caen, tardan, te limitan el ritmo y a veces cobran dos veces. Por eso parto esta sesión en dos actos, y te pido que no te saltes el segundo.

La forma del round-trip, y la ficha que ve el modelo

Antes de tocar la API quiero que tengas claras dos cosas: la forma del intercambio, que son cuatro fases y siempre las mismas, y la ficha de la tool, que es lo único que el modelo llega a ver de tu código. Ese detalle es el que más gente pasa por alto, y luego se pregunta por qué el modelo no usa bien su función.

Por qué

Fíjate en el reparto de papeles. modelo_decide solo devuelve una intención: el nombre de una tool y unos argumentos. ejecutar_tool es tu código, y es el único que hace algo de verdad. Esa separación es todo tool use. El modelo nunca ejecuta nada, ni aquí, ni con la API real. Si algo pasa en tu sistema, lo hizo tu código porque tú lo escribiste.

Por qué

Lee la description como lo que es: un prompt. Dice qué hace, cuándo usarla ("siempre que el usuario pregunte por una orden") y da un ejemplo del formato ("ORD-NNNN, p. ej. ORD-8841"). Sin ese "cuándo", el modelo la usa a destiempo; sin el ejemplo, se inventa el formato del id. El input_schema es JSON Schema: la firma de tu función traducida a algo que el modelo entiende. required no es decorativo: es lo que impide que llame la tool sin el order_id.

def run_tool(name: str, args: dict) -> str:    # Recibe el nombre de una tool pedida y sus argumentos, y decide    # qué función de Python ejecutar de verdad.    fn = TOOLS.get(name)    if fn is None:        # Si el modelo se inventó una tool que no existe, no tumbamos        # el programa: devolvemos un error en texto JSON.        return json.dumps({"error": f"tool desconocida: {name}"})    return json.dumps(fn(**args), ensure_ascii=False)    # Ejecutamos la función real con sus argumentos y convertimos el    # resultado a texto JSON para poder enviarlo de vuelta al modelo.
Por qué

El if fn is None no es paranoia: el modelo puede inventarse el nombre de una tool que no existe. Si eso tumba tu programa, un error del modelo se convierte en una caída tuya. Devolver el error como texto JSON deja que el modelo lo lea y se corrija en el turno siguiente. Y json.dumps al final: el content de un tool_result viaja como texto, nunca como diccionario de Python.

def with_backoff(fn, max_retries=5):    # Función "envoltorio": recibe OTRA función (fn) y la ejecuta con    # reintentos automáticos si falla por un error transitorio.    for attempt in range(max_retries):        # Intentamos como máximo max_retries veces (0, 1, 2, 3, 4...).        try:            return fn()            # Si fn() no lanza ningún error, devolvemos su resultado y            # terminamos aquí mismo.        except ErrorTransitorio as e:            # Solo atrapamos errores transitorios: un 400 o 401 real            # NO debería atraparse aquí, se debe dejar propagar siempre.            print(f"  intento {attempt}: falló ({e})")            if attempt == max_retries - 1:                # Si este ya era el último intento permitido, dejamos                # que el error se propague de verdad.                raise            espera = min(60, 2**attempt) * random.random()            # 2**attempt duplica la espera "base" en cada vuelta            # (1s, 2s, 4s, 8s...) sin pasar nunca de 60 segundos.            # Multiplicar por random.random() (0.0 a 1.0) es el "jitter":            # evita que muchos clientes esperen exactamente lo mismo.            print(f"    esperando {espera:.2f}s antes de reintentar...")            time.sleep(espera)
Por qué

Una sola línea contiene las tres ideas: min(60, 2**attempt) * random.random(). 2**attempt duplica la espera cada vuelta (1, 2, 4, 8…): darle tiempo real a que el servicio se recupere. min(60, …) pone techo, o el sexto intento espera un minuto largo. Y random.random() es el jitter: si cien clientes fallan a la vez y todos reintentan exactamente a los 2 segundos, vuelven a tumbar el servicio juntos. La aleatoriedad los dispersa. Lo que no hace también importa: solo atrapa ErrorTransitorio. Un 400 o un 401 se propagan. Reintentar un bug propio solo lo hace más caro.
