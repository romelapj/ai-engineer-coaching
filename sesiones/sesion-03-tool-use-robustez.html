Acto 1 — Haz que funcione

¿Dónde va mi orden ORD-8841?

Pregúntale eso a un modelo sin herramientas y solo tiene dos salidas — las dos malas:

  • Se rinde: "no tengo acceso a tus órdenes". Honesto, pero inútil.
  • Alucina: "su orden llega mañana". Suena perfecto — y es falso.
  • El modelo no puede saber lo que no está en su contexto. Tool use es el arreglo: él decide qué hacer, tu código lo hace.

Hoy construimos tool_loop.py — un asistente de soporte e-commerce — pieza a pieza: 4 pasos para que funcione, 4 pilares para que sobreviva.

Acto 1 — Haz que funcione

Anatomía del round-trip

1️⃣

Pide

El modelo responde con un bloque tool_use: el nombre de la tool y sus argumentos en JSON. Lo detectas en stop_reason == "tool_use".

2️⃣

Ejecutas

Tu código corre la función. El modelo nunca ejecuta nada: solo emite la intención; las manos las pones tú.

3️⃣

Devuelves

El resultado vuelve como tool_result dentro de un mensaje con rol user, enlazado por su tool_use_id.

4️⃣

Responde

Con el resultado en contexto, el modelo responde al usuario — o pide otra tool, y el ciclo se repite.

Ese es todo el modelo mental. Ahora lo convertimos en código: una pieza por paso, sobre el mismo archivo.

Acto 1 · Paso 1 de 4

La tool: la descripción ES el prompt

El modelo solo ve tres cosas: name, description e input_schema. La calidad de tu tool calling depende más de la descripción que de tu código.

input_schema es JSON Schema (el estándar de OpenAPI): la firma de tu función traducida a JSON — qué argumentos existen, de qué tipo y cuáles son obligatorios. El modelo lo lee todo: los description y enum de cada propiedad también son prompt.

  • ❌ "orders" / "Gets orders" — el modelo la ignora o inventa argumentos.
  • ✅ Nombre con verbo + objeto, en snake_case.
  • ✅ 3–4 frases: qué hace, qué devuelve y cuándo usarla.
  • ✅ Formato del input con ejemplo concreto.
  • ✅ required explícito; enums para valores cerrados. 
# tool_loop.py — paso 1: la tool
ORDERS = {"ORD-8841": {"status": "shipped",
                       "eta": "2026-07-04"}}

def get_order_status(order_id: str) -> dict:
    return ORDERS.get(
        order_id, {"error": "orden no existe"})

tools = [{
  "name": "get_order_status",
  "description": (
    "Consulta el estado de una orden y su "
    "fecha estimada de entrega. Úsala siempre "
    "que el usuario pregunte por una orden. "
    "ID formato ORD-NNNN, p. ej. ORD-8841."
  ),
  "input_schema": {      # JSON Schema: el contrato de los args
    "type": "object",     # siempre object: viajan como kwargs
    "properties": {       # cada parámetro y su tipo JSON
      "order_id": {"type": "string"},
    },
    "required": ["order_id"],  # si no está aquí, es opcional
  },
}]
Acto 1 · Paso 2 de 4

El loop: tool_use → tool_result

# tool_loop.py — paso 2: el loop. Pide, ejecutas, devuelves, responde.
import json
import anthropic

client = anthropic.Anthropic()  # en el pilar 3 (slide 13) se reconfigura con timeout y max_retries

TOOLS = {"get_order_status": get_order_status}

def run_tool(name: str, args: dict) -> str:  # despacha por nombre
    fn = TOOLS.get(name)
    if fn is None:  # tool desconocida: el modelo se entera, no revientas
        return json.dumps({"error": f"tool desconocida: {name}"})
    return json.dumps(fn(**args), ensure_ascii=False)  # string, no dict

messages = [{"role": "user", "content": "¿Dónde va mi orden ORD-8841?"}]
for _ in range(10):  # presupuesto de pasos — nunca while True
    resp = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=1024,
        tools=tools, messages=messages,
    )
    if resp.stop_reason != "tool_use":
        break  # respuesta final para el usuario
    messages.append({"role": "assistant", "content": resp.content})
    results = [
        {"type": "tool_result", "tool_use_id": b.id,
         "content": run_tool(b.name, b.input)}
        for b in resp.content if b.type == "tool_use"
    ]
    messages.append({"role": "user", "content": results})

print("".join(b.text for b in resp.content if b.type == "text"))

Tres errores clásicos: olvidar reinyectar el turno assistant completo; pasar el dict crudo en content (va serializado con json.dumps); y el loop sin tope — un agente confundido con while True te quema el budget. El presupuesto va en el código, no en un TODO.

Acto 1 · Paso 3 de 4

Tool calls en paralelo

"Compara mis órdenes ORD-8841 y ORD-9200" — un solo turno del modelo trae dos bloques tool_use a la vez. Nuestro loop ya los recorre; falta ejecutarlos bien.

  • Regla de oro: responde TODOS los tool_use en un solo mensaje user, cada uno con su tool_use_id.
  • Un tool_use sin tool_result = 400 invalid_request_error en el siguiente turno.
  • Ejecuta concurrente con asyncio.gather o ThreadPoolExecutor: 3 tools de 2 s pasan de 6 s secuenciales a ~2 s.
  • Si una tool falla, no rompas el lote: devuelve su resultado con "is_error": true y deja que el modelo decida. 
# tool_loop.py — paso 3: el lote en paralelo
from concurrent.futures import ThreadPoolExecutor

calls = [b for b in resp.content
         if b.type == "tool_use"]

# run_tool_safe = run_tool + try/except que devuelve
# un NamedTuple con .content y .failed — la escribes en el Acto 2
with ThreadPoolExecutor() as ex:
    outs = ex.map(run_tool_safe, calls)

results = [
    {"type": "tool_result",
     "tool_use_id": b.id,
     "content": out.content,
     "is_error": out.failed}
    for b, out in zip(calls, outs)
]
Acto 1 · Paso 4 de 4

JSON garantizado: tool_choice + Pydantic

En el reto 01 extraías JSON con prompts, parsing tolerante y rezos. Esto es lo que la API hace por ti: tool_choice fuerza la "llamada" — y el input de la tool es tu JSON. 

# tool_loop.py — paso 4: cierre del caso con JSON garantizado
from pydantic import BaseModel, ValidationError

class CaseSummary(BaseModel):
    order_id: str
    status: str
    next_action: str

summary_tool = {"name": "save_case_summary",
                "description": "Guarda el resumen del caso",
                "input_schema": CaseSummary.model_json_schema()}

for attempt in range(3):
    resp = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=1024,
        tools=[summary_tool],
        tool_choice={"type": "tool", "name": "save_case_summary"},
        messages=messages,
    )
    block = next(b for b in resp.content if b.type == "tool_use")
    try:
        summary = CaseSummary.model_validate(block.input)
        break
    except ValidationError as err:  # reinyecta el error y reintenta
        messages.append({"role": "assistant", "content": resp.content})
        messages.append({"role": "user", "content": [{
            "type": "tool_result", "tool_use_id": block.id,
            "content": f"Corrige y reintenta: {err}", "is_error": True}]})

El schema valida tipos y campos; Pydantic agrega reglas de negocio (status dentro de un enum, fechas reales). 2–3 reintentos con el error reinyectado corrigen la gran mayoría de outputs inválidos.

Trata al LLM como a cualquier servicio externo: todo lo que devuelve es input no confiable, y toda llamada de red va a fallar tarde o temprano. Lo que separa una demo de un producto no es el prompt — es lo que pasa cuando algo sale mal.

Acto 2 · Pilar 1 de 4

Retries: backoff exponencial + jitter

# tool_loop.py — pilar 1: la llamada ya no va directa
import random, time, anthropic

def with_backoff(fn, max_retries=5):
    for attempt in range(max_retries):
        try:
            return fn()
        except (anthropic.RateLimitError,        # 429
                anthropic.InternalServerError,   # 500 / 529
                anthropic.APITimeoutError):
            if attempt == max_retries - 1:
                raise
            # full jitter: 1s, 2s, 4s, 8s... cap 60s, × random
            time.sleep(min(60, 2 ** attempt) * random.random())

# y en el loop del paso 2, la llamada queda envuelta:
resp = with_backoff(lambda: client.messages.create(...))

# la promesa del paso 3: run_tool_safe envuelve run_tool sin romper el lote
from collections import namedtuple

ToolOut = namedtuple("ToolOut", ["content", "failed"])  # campos .content / .failed

def run_tool_safe(block):  # recibe el bloque tool_use completo, no name+args
    try:
        return ToolOut(run_tool(block.name, block.input), False)
    except Exception as e:  # una tool que revienta no tumba el turno
        return ToolOut(json.dumps({"error": str(e)}), True)
  • ¿Por qué jitter? 100 clientes que fallan juntos y reintentan a los 2 s exactos crean una retry storm: el jitter los dispersa.
  • El SDK ya trae max_retries=2 por defecto — súbelo con anthropic.Anthropic(max_retries=4) antes de escribir el tuyo.
  • Nunca reintentes 400 (request mal armado) ni 401/403 (credenciales): reintentar un bug solo lo hace más caro.
Acto 2 · Pilar 2 de 4

Rate limits: 429, 529 y qué hacer con cada error

La regla de decisión en una línea: ¿es culpa tuya? No reintentes. ¿Es transitorio? Backoff. La tabla es el detalle:

Código Error Significa Acción
429 rate_limit_error Superaste tu cuota: RPM, input tokens/min u output tokens/min Espera lo que diga el header retry-after, luego backoff
529 overloaded_error La API está sobrecargada — no es culpa tuya Backoff + jitter; degrada con gracia si persiste
500 api_error Error interno transitorio del servidor Reintentar con backoff (suele resolverse en 1–2 intentos)
400 invalid_request_error Tu request está mal (schema, tool_result faltante…) NO reintentar — loggear y arreglar el código

Pro tip: lee anthropic-ratelimit-requests-remaining en los headers y frena antes del 429 — throttling proactivo gana a reactivo.

Acto 2 · Pilar 3 de 4

Timeouts e idempotencia

# tool_loop.py — pilar 3: el cliente, bien configurado
client = anthropic.Anthropic(timeout=30.0, max_retries=4)

⏱️ Timeouts

  • Default del SDK: 10 minutos. Para un chatbot interactivo eso es una eternidad — baja a 30–60 s: Anthropic(timeout=30.0).
  • Trade-off: timeout corto mejora la latencia p99 percibida, pero genera más retries → más costo en tokens.
  • Respuestas largas: usa streaming — el primer token llega en segundos y resetea tu percepción de "colgado".

🔂 Idempotencia

  • Un timeout no garantiza que el request falló: pudo completarse. Reintentar una tool que cobra o envía email = cobro doble, email doble.
  • Tools con side effects: idempotency key por operación o check "¿ya existe?" antes de ejecutar.
  • Diseño primero: haz las tools read-only cuando se pueda, y separa "proponer acción" de "confirmar acción".
Acto 2 · Pilar 4 de 4

Logging: si no lo logueaste, no pasó

Lo mínimo por cada llamada al modelo:

  • request_id — es lo que soporte de Anthropic te va a pedir para investigar
  • usage.input_tokens / output_tokens — tu factura vive aquí
  • stop_reason — max_tokens aquí = respuesta truncada silenciosa
  • Latencia y número de intento (¿cuántos retries costó?)
  • Por tool call: nombre, input, duración y resultado truncado a ~500 chars 
# tool_loop.py — pilar 4: cada llamada deja rastro
import logging

logging.basicConfig(level=logging.INFO)
log = logging.getLogger("tool_loop")  # los campos de extra requieren un formatter propio para verse

t0 = time.monotonic()
resp = with_backoff(lambda: client.messages.create(...))

log.info("llm_call", extra={
    "request_id": resp._request_id,
    "model": resp.model,
    "stop_reason": resp.stop_reason,
    "in_tok": resp.usage.input_tokens,
    "out_tok": resp.usage.output_tokens,
    "latency_s": time.monotonic() - t0,
})
