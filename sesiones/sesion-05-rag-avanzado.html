Dónde se rompe el vector search puro

Los embeddings brillan en…

  • Paráfrasis: "¿cómo devuelvo un pago?" ≈ "reembolsar una transacción"
  • Sinónimos y queries vagas o conversacionales
  • Similitud semántica entre idiomas cercanos

…y fallan en lo exacto

  • Códigos y IDs: "error E-4012" recupera docs de errores… pero no ese error
  • Siglas y jerga interna: "RRF", "TAM", "SKU-9981"
  • Nombres propios y de producto: "endpoint v3 de Checkout Lite"
  • Keywords raras: el embedding las "suaviza" hacia el tema general

Síntoma típico: el usuario pega un término literal del documento y el chunk correcto ni aparece en el top-10. Eso no se arregla con un mejor prompt: se arregla en el retrieval.

Golden set: recall@k y MRR, el instrumento primero

Una mejora de retrieval sin métrica es una anécdota. Con golden set, es un dato que puedes defender en un PR.
  • Golden set: 20–50 queries reales mapeadas al chunk que debería salir. Hazlo a mano: 1 hora bien invertida.
  • recall@k: ¿en qué fracción de queries el chunk correcto está en el top-k? Tu métrica principal.
  • MRR: promedio de 1/posición del primer acierto. Premia que lo correcto salga arriba, no solo que salga. 
def recall_at_k(golden, results, k=5):
    hits = sum(1 for q in golden
               if golden[q] in results[q][:k])
    return hits / len(golden)

def mrr(golden, results):
    total = 0.0
    for q in golden:
        if golden[q] in results[q]:
            total += 1 / (results[q].index(golden[q]) + 1)
    return total / len(golden)

Con el instrumento montado, cada técnica que sigue se prueba contra él: la activas, mides y comparas. Sin esto, todo lo demás es fe.

Búsqueda híbrida: BM25 + vectores con RRF

BM25 puntúa por coincidencia léxica (TF-IDF con saturación): es exacto donde el embedding es difuso. Reciprocal Rank Fusion mezcla ambos rankings sin calibrar scores: solo usa posiciones. 

# RRF: score(doc) = Σ 1 / (k + rank)  (k=60 es el estándar)
def rrf(rankings, k=60):
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)
    return sorted(scores, key=scores.get, reverse=True)

# corpus = textos de tus chunks; ids = sus doc_ids (mismo orden), del índice del reto 3.
from rank_bm25 import BM25Okapi  # pip install rank_bm25
bm25 = BM25Okapi([c.split() for c in corpus])
bm25_scores = bm25.get_scores(query.split())
bm25_top50 = [ids[i] for i in bm25_scores.argsort()[::-1][:50]]

# el vector search del reto 3, pero pidiendo doc_ids (no textos):
vector_top50 = collection.query(query_texts=[query], n_results=50)["ids"][0]
id_a_chunk = dict(zip(ids, corpus))  # para rehidratar tras la fusión

fused = rrf([bm25_top50, vector_top50])[:20]  # top-20 → al reranker
rehidratados = [id_a_chunk[i] for i in fused]

10 líneas, cero modelos nuevos, y suele subir recall@5 entre 5 y 15 puntos en corpus con jerga técnica. Es la mejora con mejor ROI de toda la sesión. Aun así: actívalo, corre el golden set y deja que el número decida.

Rerankers: precisión cara, úsala al final

Un cross-encoder lee query y documento juntos y produce un score de relevancia real, mucho más preciso que comparar dos vectores precalculados, pero imposible de usar sobre todo el corpus.

Bi-encoder (vectores) Cross-encoder (reranker)
Cómo compara Embeddings precalculados, similitud coseno Atención conjunta query + doc en inferencia
Escala Millones de docs en ~10 ms (ANN) Solo 20–100 candidatos, ~100–300 ms extra
Rol en el pipeline Recuperar top-50 barato Reordenar y quedarse con el top-5
Opciones voyage-3, text-embedding-3, bge-m3 Cohere Rerank, bge-reranker-v2, ms-marco MiniLM

Regla de decisión: si tu recall@50 es alto pero tu recall@5 es bajo, el reranker paga su latencia. Si recall@50 ya es malo, el problema está antes: arregla el retrieval, no el orden. Como siempre: actívalo, corre el golden set y deja que el número decida.

Query rewriting y expansión

La query del usuario no es la query óptima para tu índice. Un paso barato con un LLM expande siglas, agrega sinónimos y resuelve referencias del historial ("¿y el segundo paso?"). 

import anthropic

client = anthropic.Anthropic()

def rewrite(query: str) -> str:
    resp = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=200,
        system="Reescribe la query para un motor de búsqueda. "
               "Expande siglas y agrega sinónimos clave. "
               "Devuelve SOLO la query reescrita.",
        messages=[{"role": "user", "content": query}],
    )
    return resp.content[0].text

# "qué pasa si falla el 3DS" →
# "fallo de autenticación 3DS (3-D Secure) en pagos: causas y manejo de errores"

Costo: una llamada corta (~300–500 ms). No todo paso "avanzado" gana en tu corpus: actívalo, corre el golden set y deja que el número decida: si no sube recall, quítalo.

Metadata filtering: reduce el espacio antes de buscar

  • Filtra antes de la similitud: año, producto, idioma, tipo de doc, tenant. "Política de vacaciones 2026" → year=2026 AND type=policy y luego vector search.
  • Pre-filter > post-filter: filtrar después del top-k puede dejarte con 0 resultados válidos aunque existan en el corpus.
  • Access control es metadata: el RAG nunca debe recuperar chunks que el usuario no puede leer. Esto es seguridad, no relevancia.

Self-query con LLM

Usa el modelo para extraer filtros estructurados de la query en lenguaje natural: "facturas de Acme de marzo" → {"cliente": "Acme", "mes": 3} + query semántica "facturas". Es el mismo patrón de tool use que ya conoces de la Fase 1.

Filtrar cambia qué recuperas, no solo cuánto: actívalo, corre el golden set y deja que el número decida.

Mejoras de indexación · se pagan una vez

Contextual retrieval (Anthropic)

Un chunk suelto pierde contexto: "la tasa subió 3%". ¿De qué, cuándo, de quién? La idea: antes de indexar, pedirle al modelo 2–3 frases que sitúen el chunk dentro de su documento, y embeber chunk + contexto. 

# 1 llamada por chunk; en la sesión 09 verás prompt caching para no repagar el doc completo
for doc, fuente in documentos:  # tus documentos del reto 3: (texto, fuente)
    for chunk in chunk_markdown(doc, fuente):  # chunks (dict) de la sesión 04
        prompt = f"""<document>{doc}</document>
Sitúa este chunk dentro del documento:
<chunk>{chunk['texto']}</chunk>
Responde SOLO con 2-3 frases de contexto."""

        resp = client.messages.create(
            model="claude-sonnet-4-6",
            max_tokens=150,
            messages=[{"role": "user", "content": prompt}],
        )
        chunk_indexable = resp.content[0].text + "\n\n" + chunk["texto"]

Cifras del paper de Anthropic (tasa de fallo del top-20): embeddings contextuales −35%; + BM25 contextual −49%; + reranking −67%. Es preprocesamiento: pagas una vez al indexar, no en cada query.

Mejoras de indexación · se pagan una vez

Parent-document retrieval: busca chico, entrega grande

El conflicto

  • Chunks pequeños (200–400 tokens) → embeddings precisos, matching fino
  • Chunks grandes → el LLM tiene contexto para responder bien
  • Un solo tamaño de chunk siempre sacrifica uno de los dos

El patrón

  • Indexa y busca con chunks hijos pequeños
  • Al recuperar, entrega al modelo la sección o documento padre
  • Trade-off: más tokens al generador → más costo y latencia por respuesta

Combina bien con contextual retrieval: uno mejora encontrar, el otro mejora responder. Y como todo en esta sesión: actívalo, corre el golden set, y deja el número decidir.
