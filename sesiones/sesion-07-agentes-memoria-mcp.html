Objetivos de la sesión

La memoria es la columna vertebral de hoy: es lo que construyes en el lab. Multi-agente y MCP son las dos extensiones que le cuelgas encima una vez que el agente ya recuerda.

Gestionar contexto

columna vertebral

Sobrevivir tareas largas con compaction y memoria externa: qué comprimir, qué persistir y dónde.

Decidir multi-agente

extensión

Cuándo el patrón orquestador-trabajadores paga el 15× de tokens que cuesta, y cuándo es overengineering.

Entender MCP

extensión

El protocolo que convierte N×M integraciones en N+M: servers, tools y resources.

El contexto es un recurso finito (y caro)

El problema

  • claude-sonnet-4-6 tiene ventana de 1M tokens, pero la calidad degrada antes de llenarla: context rot, el modelo pierde precisión con contexto saturado de tool results viejos.
  • La API es stateless: en cada turno reenvías TODO el historial.
  • 100K tokens de historial × $3/MTok = $0.30 por llamada. Un loop de 50 turnos: $15+ solo en input.

Las 3 palancas

  • Recortar: descarta tool results viejos que ya no aportan (context editing).
  • Comprimir: resume lo viejo en un párrafo (compaction). Pierdes detalle, conservas decisiones.
  • Externalizar: saca el estado del contexto a archivos o DB y recupéralo solo cuando haga falta.

Bonus: prompt caching baja las relecturas a ~0.1× el precio (cómo activarlo, en la Sesión 09).

Compaction: resume lo viejo, conserva lo reciente

# cuando el historial crece, comprime los turnos viejos en un resumen
import anthropic

client = anthropic.Anthropic()

def compact(messages: list) -> list:
    resumen = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=1024,
        system="Resume esta conversación: decisiones tomadas, estado actual y pendientes.",
        messages=messages[:-6],          # todo menos los últimos turnos
    )
    return [
        {"role": "user",
         "content": f"[Resumen de la sesión]\n{resumen.content[0].text}"},
        *messages[-6:],                  # lo reciente queda intacto
    ]

La API también ofrece compaction server-side (beta compact-2026-01-12): resume sola al acercarse al límite. Regla práctica: dispara la compactación al ~70% del presupuesto de contexto, nunca cuando ya reventó.

Memoria de corto vs largo plazo

Corto plazo = context window

  • Vive solo durante la sesión: muere con el proceso
  • Acceso inmediato, sin retrieval
  • Cara: la pagas completa en cada llamada
  • Ejemplos: historial de turnos, tool results, scratchpad del turno actual

Largo plazo = archivos / DB

  • Sobrevive reinicios y sesiones
  • Barata de almacenar, pero exige decidir qué leer y cuándo
  • Formatos: archivo Markdown/JSON, SQLite, vector DB si necesitas búsqueda semántica
  • Ejemplos: preferencias del usuario, lecciones aprendidas, estado de tareas multi-día

El patrón MEMORY.md que usa Claude Code es esto: un archivo que el agente lee al arrancar y edita cuando aprende algo. Empieza con un archivo plano; una vector DB solo cuando la memoria no quepa en el contexto.

Memoria persistente como tool

import json, pathlib

MEM = pathlib.Path("memoria.json")

def memory_write(key: str, value: str) -> str:
    data = json.loads(MEM.read_text()) if MEM.exists() else {}
    data[key] = value
    MEM.write_text(json.dumps(data, ensure_ascii=False, indent=2))
    return f"guardado: {key}"

tools = [{
    "name": "memory_write",
    "description": "Guarda un hecho que debas recordar en futuras sesiones.",
    "input_schema": {"type": "object",
        "properties": {"key": {"type": "string"},
                       "value": {"type": "string"}},
        "required": ["key", "value"]},
}]

resp = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    # la memoria entra por el system prompt; el modelo decide cuándo escribir
    system=f"Tu memoria persistente:\n{MEM.read_text() if MEM.exists() else '{}'}",
    tools=tools,
    messages=[{"role": "user", "content": "Mi stack es Python + FastAPI"}],
)

Lectura barata (system prompt) + escritura explícita (tool). Anthropic ofrece un memory tool oficial (memory_20250818) con esta misma idea: tú implementas el backend de archivos.

Multi-agente: orquestador-trabajadores

Ya sabes que tu agente recuerda entre sesiones. El siguiente límite no es la memoria: es cuando el trabajo intermedio no cabe en un solo contexto. Ahí dejas de agrandar el loop y empiezas a delegar.

  • Orquestador: descompone la tarea, delega y consolida resultados. No ejecuta el trabajo pesado.
  • Trabajadores (subagentes): cada uno con contexto limpio, system prompt especializado y el mínimo de tools. Devuelven el resultado, no el proceso.
  • El beneficio real es aislamiento de contexto: 50K tokens de logs explorados por un worker llegan al orquestador como 500 tokens de hallazgos.

Los números de Anthropic

Su sistema de research multi-agente superó al mejor agente único en ~90% en su eval interna de investigación…

…gastando ~15× más tokens que un chat normal (un agente solo ya gasta ~4×).

Multi-agente compra calidad y paralelismo con tokens. Esa es la ecuación que tienes que justificar.

Un subagente son 10 líneas

def subagente(tarea: str, rol: str) -> str:
    # contexto LIMPIO: no hereda el historial del orquestador
    resp = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=2048,
        system=rol,
        messages=[{"role": "user", "content": tarea}],
    )
    return resp.content[0].text

logs = open("app.log").read()  # cualquier texto de logs que quieras analizar
hallazgos = subagente(
    tarea=f"Analiza estos logs y lista los errores 5xx con su causa probable:\n{logs}",
    rol="Eres analista de logs de producción. Devuelve solo hallazgos, sin paja.",
)
# el orquestador recibe el RESULTADO (~500 tokens), no el proceso (~50K)

La interfaz importa más que el framework: tarea bien especificada de entrada, resultado compacto de salida. Si el subagente necesita preguntarte cosas a mitad de camino, la descomposición estuvo mal.

¿Cuándo vale la pena el multi-agente?

Sí

  • Subtareas paralelizables e independientes (investigar 10 fuentes, revisar 30 archivos)
  • El trabajo intermedio no cabe en un solo contexto
  • Tareas read-heavy donde el valor justifica el costo

No

  • Pasos secuenciales con estado compartido: los agentes no comparten contexto y se descoordinan
  • Workflows latency-sensitive: cada subagente suma llamadas
  • Cuando un solo agente con mejores tools resolvería igual
Multi-agente es una optimización, no un punto de partida: empieza con un agente y buenas tools; agrega subagentes cuando el contexto, no tu arquitectura, te lo pida.

MCP: de N×M a N+M

Memoria y subagentes resuelven cómo piensa tu agente. Falta con qué actúa: sus herramientas. Cablear cada agente a cada herramienta a mano no escala, y justo eso es lo que MCP estandariza.

Antes: cada app de IA × cada integración = un adaptador ad-hoc (5 apps × 8 herramientas = 40 integraciones). Con Model Context Protocol (Anthropic, nov 2024; hoy adoptado también por OpenAI y Google): cada app implementa 1 cliente, cada herramienta 1 server = 13 piezas. Protocolo abierto sobre JSON-RPC, transporte stdio o HTTP.

Primitiva Quién la controla Ejemplo
Tools El modelo decide invocarlas buscar_notas(query), crear_ticket(...)
Resources La aplicación las adjunta como contexto notas://recientes, un archivo, un esquema de DB
Prompts El usuario las invoca (slash commands) /revisar-pr con plantilla predefinida

Los MCP servers que usas en Claude Code (GitHub, Slack, Jira…) son exactamente esto: procesos que exponen tools y resources por un protocolo común.

Un MCP server mínimo en Python

# server.py: pip install "mcp[cli]"
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("notas-equipo")
NOTAS = ["usa retries con backoff", "el default mutable es un bug"]

# tool: el modelo decide cuándo llamarla
@mcp.tool()
def buscar_notas(query: str) -> str:
    """Busca en las notas técnicas del equipo."""
    return "\n".join(n for n in NOTAS if query in n)

# resource: la app lo adjunta como contexto
@mcp.resource("notas://recientes")
def notas_recientes() -> str:
    return "\n".join(NOTAS[-10:])

if __name__ == "__main__":
    mcp.run()  # transporte stdio por defecto

El docstring ES la descripción que ve el modelo: escríbelo como instrucción de cuándo usarla. Del lado cliente, el SDK de anthropic trae helpers (anthropic[mcp]) para convertir tools MCP y pasarlas al tool runner.

Manos al código · 30 min en pareja

Construimos juntos un agente CLI con memoria persistente: un asistente que recuerda tu stack y tus preferencias aunque mates el proceso.

  • Min 0–10 · tools memory_write y memory_read respaldadas por memoria.json (el código de la slide 7 es tu punto de partida)
  • Min 10–20 · loop de tool use: mientras stop_reason == "tool_use", ejecuta la tool y devuelve el tool_result con su tool_use_id
  • Min 20–25 · la prueba de fuego: cuéntale tu stack, mata el proceso, relanza y pregúntale qué recuerda
  • Min 25–30 · inyecta la memoria al system prompt en el arranque y compara: ¿cuándo conviene tool de lectura vs system prompt?

Definición de éxito: el agente responde "Python + FastAPI" en una sesión nueva sin que se lo repitas.

Agente con memoria

Un agente con memoria persistente entre ejecuciones (archivo o DB, tú eliges) que además delegue trabajo a un subagente especializado con contexto limpio y rol propio. Criterios: la memoria sobrevive al reinicio del proceso, el subagente devuelve resultados compactos al orquestador, y puedes explicar qué guardaste en memoria y por qué.

Bonus: expón la memoria como un MCP server propio y conéctalo a Claude Code o a tu cliente MCP favorito.

Enunciado completo y rúbrica: gym/reto-06-agente-con-memoria

Seguridad: el hilo que cruza los tres pilares

Todo lo de hoy abre superficie de ataque: la memoria externa puede envenenarse, cada subagente amplía el set de tools, y un MCP server trae herramientas de terceros. Una sola disciplina las cruza: trata todo lo que entra al contexto como no confiable.

La trifecta letal

Un agente es explotable vía prompt injection cuando combina las tres a la vez:

  • Acceso a datos privados
  • Exposición a contenido no confiable (web, emails, tool results)
  • Capacidad de exfiltrar (HTTP, email, escribir fuera)

Elimina una de las tres y el ataque pierde el camino de salida.

Reglas mínimas

  • Mínimo privilegio: cada subagente solo las tools que necesita; allowlists, no blocklists
  • Sandboxing: ejecución de código en contenedor sin red o con egress restringido
  • Human-in-the-loop: confirmación para acciones destructivas o irreversibles (deploy, delete, enviar)
  • Tool results = input no confiable: lo que vuelve de la web puede traer instrucciones inyectadas
  • Secretos fuera del prompt: API keys en el entorno del harness, nunca en el contexto

Checklist de salida

  • Sé explicar las 3 palancas de context management: recortar, comprimir (compaction), externalizar, y cuándo usar cada una
  • Distingo memoria de corto plazo (context window) de largo plazo (archivos/DB) y sé implementar la segunda como tool
  • Puedo justificar con números (calidad vs ~15× tokens) cuándo multi-agente sí y cuándo es overengineering
  • Entiendo qué resuelve MCP (N×M → N+M) y la diferencia entre tools, resources y prompts
  • Conozco la trifecta letal y las reglas mínimas: mínimo privilegio, sandboxing, human-in-the-loop
  • Tengo el agente CLI con memoria del pair programming corriendo en mi máquina
  • Reto 06 leído y agendado antes de la próxima sesión
