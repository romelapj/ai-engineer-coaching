Workflows vs agentes · "Building Effective Agents"

Workflow

  • Tu código orquesta; los LLMs rellenan pasos predefinidos.
  • Patrones: prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer.
  • Predecible y testeable: el mismo camino en cada ejecución.
  • Úsalo cuando conoces los pasos de antemano.

Agente

  • El LLM dirige su propio proceso: decide qué tool llamar y cuándo terminar.
  • El camino emerge en runtime; no es conocible a priori.
  • Flexible pero caro: cada paso reenvía el historial completo.
  • Úsalo cuando no puedes hardcodear el camino: debugging, research, coding.

Regla de Anthropic: busca la solución más simple posible y sube de complejidad solo si la tarea lo exige. La mayoría de "agentes" en producción son workflows, y está bien.

La idea fuerza

Un agente es un LLM usando herramientas en un loop. Eso es todo.

Recuerda el tool use de la sesión 03: el modelo pedía una herramienta, tú la ejecutabas y le devolvías el resultado. Un agente es exactamente eso, pero en un loop que el modelo controla hasta decidir que terminó.

Memoria, planning, multi-agente, MCP… todo lo que verás después son extensiones de este loop de ~30 líneas. Si entiendes el loop, ningún framework te va a intimidar, porque sabrás exactamente qué esconden debajo.

Anatomía del loop

Decide

El modelo ve el historial y elige: ¿respondo o llamo una tool? Lo lees en stop_reason: "tool_use" o "end_turn".

Ejecuta

Tu código corre la tool. El modelo nunca ejecuta nada: solo emite JSON con nombre y argumentos.

Observa

El resultado vuelve como tool_result dentro de un mensaje con rol user, enlazado por tool_use_id.

Repite

Hasta que el modelo decida terminar (end_turn) o tú agotes el presupuesto de pasos. Nunca while True.

El loop completo, sin frameworks

# agent.py: esto ES el agente. Todo lo demás es decoración.
import anthropic

client = anthropic.Anthropic()
MAX_STEPS = 10
messages = [{"role": "user", "content": "Investiga el tema X y cita fuentes"}]

for step in range(MAX_STEPS):          # presupuesto, no while True
    resp = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=4096,
        tools=TOOLS,  # ← la lista TOOLS se define en la slide 9 (Tool bien diseñada)
        messages=messages,
    )
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":
        break                            # 1. DECIDE: el modelo terminó
    results = [{"type": "tool_result", "tool_use_id": b.id,
                "content": run_tool(b.name, b.input)}   # 2. EJECUTA: run_tool también en la slide 9
               for b in resp.content if b.type == "tool_use"]
    messages.append({"role": "user", "content": results})  # 3. OBSERVA → 4. REPITE

Fíjate: el historial messages crece en cada paso y se reenvía completo. Esa es la memoria de trabajo del agente, y también su costo.

Diseño de tools: 3 reglas que separan junior de senior

Descripciones = onboarding

Escribe la description como si entrenaras a un nuevo dev: qué hace, cuándo usarla, cuándo NO, qué formato devuelve. El modelo solo sabe lo que tú le cuentas.

Errores accionables

Nunca lances excepciones al loop ni devuelvas "error" a secas. Devuelve qué falló y qué probar después: el modelo se autocorrige si le das con qué.

Granularidad correcta

Pocas tools, sin solapamiento, a prueba de errores. Ejemplo de Anthropic en SWE-bench: exigir rutas absolutas en vez de relativas eliminó una clase entera de fallos.

Métrica práctica: si tú no sabrías cuál de dos tools usar leyendo solo sus descripciones, el modelo tampoco.

Tool bien diseñada: descripción y error

import httpx  # pip install httpx
from markdownify import markdownify as to_markdown  # pip install markdownify

TOOLS = [{
    "name": "fetch_page",
    "description": ("Descarga una URL y devuelve su texto en markdown "
        "(máx 8.000 chars). Úsala DESPUÉS de search_web, con una URL "
        "exacta de sus resultados. No soporta PDFs ni páginas con login."),
    "input_schema": {"type": "object", "required": ["url"],
        "properties": {"url": {"type": "string",
            "description": "URL completa con https://"}}},
}]

def fetch_page(url: str) -> str:
    try:
        r = httpx.get(url, timeout=10, follow_redirects=True)
        r.raise_for_status()  # 4xx/5xx → lanza httpx.HTTPStatusError (cae al except)
        return to_markdown(r.text)[:8000]   # truncar: el contexto es presupuesto
    except httpx.HTTPStatusError as e:
        # error INFORMATIVO: dice qué pasó y qué hacer después
        return (f"ERROR {e.response.status_code} al abrir {url}. "
                "Prueba otra URL de los resultados de búsqueda.")

# mismo patrón de dispatch que en la S03, con la tool de hoy
TOOLS_MAP = {"fetch_page": fetch_page}

def run_tool(name: str, args: dict) -> str:
    return TOOLS_MAP[name](**args)

Stopping conditions y presupuestos

Condición Implementación Nota de coach
El modelo termina stop_reason == "end_turn" La salida feliz. No la asumas: verifícala.
Presupuesto de pasos for step in range(MAX_STEPS) 8–15 para research. while True = factura abierta.
Presupuesto de tokens acumula resp.usage.input_tokens + output_tokens Con historial creciente, 10 pasos pueden costar 30–50× una llamada simple.
Timeout de reloj import time
t0 = time.monotonic() (antes del loop)
time.monotonic() - t0 > 120 		Protege contra tools lentas (red, scraping).
Respuesta cortada stop_reason == "max_tokens" La salida quedó incompleta: no la entregues como final.

Al agotar presupuesto, haz una última llamada sin tools: "entrega el mejor informe posible con lo que tienes". Nunca devuelvas vacío.

Checklist de descarte: ¿de verdad necesitas un agente?

Antes de escribir el loop, corre esta lista. Marcar una sola casilla ya es razón para NO usar agente: resuélvelo con un workflow o una llamada directa.

  • El camino es predecible: puedes mapear los pasos de antemano → workflow encadenado, determinista y testeable.
  • No hay señal de verificación: nada (tests, errores, resultados) le dice al modelo si un paso salió bien; el loop deriva sin rumbo.
  • La latencia es dura: un SLA de p95 < 2 s no aguanta 10 round-trips al modelo.
  • Los errores son caros e irreversibles: pagos o borrados sin checkpoint humano, incidente esperando fecha.
  • Una sola llamada con buen prompt ya resuelve: el caso más común y el más ignorado.
Test de Barry Zhang (Anthropic): construye un agente solo si la tarea es ambigua, valiosa y verificable a la vez. Si falla una, no es para agente.

Frameworks vs from-scratch, y qué decir en entrevista

From-scratch (API directa)

  • El loop son ~30 líneas: control total del prompt y el contexto.
  • Debug = leer un print por paso. Ves cada token que pagas.
  • Cero dependencias que se rompan con cada release.

LangGraph, CrewAI, Agents SDK…

  • Te regalan checkpointing, retries, streaming, human-in-the-loop.
  • Costo: capas de abstracción que esconden el prompt final que se envía.
  • Útiles en producción cuando ya entiendes lo que hacen por debajo.

En entrevista: "empiezo con la API directa porque necesito ver cada prompt; adopto un framework cuando el proyecto pide persistencia o human-in-the-loop en producción". Eso te contrata. "Uso LangChain porque es el estándar" sin poder explicar el loop. Eso te descarta.

Manos al código · agente "wiki-researcher" (30 min)

Construimos juntos, en un solo agent.py, un agente que responde preguntas factuales con fuentes usando la API de Wikipedia. Sin frameworks.

  • Min 0–5 · definir TOOLS: search_wikipedia(query) y get_article(title), con descripciones estilo onboarding.
  • Min 5–15 · escribir el loop con MAX_STEPS = 8 y una traza por consola: paso, tool llamada y argumentos.
  • Min 15–25 · correrlo con "¿qué países han ganado más de 3 mundiales y en qué años?" y leer la trayectoria completa paso a paso.
  • Min 25–30 · romperlo a propósito: devolver un error genérico vs uno informativo y comparar cómo se recupera el modelo.
