Objetivos de la sesión

Instrumentar

Trazas, tokens, costos y latencia en cada llamada al LLM, visibles en un dashboard, no en tu imaginación.

Recortar costo

Aplicar prompt caching y elegir el modelo correcto por tarea: pequeño para lo simple, grande para lo difícil.

Bajar latencia percibida

Streaming para que el primer token llegue en menos de un segundo, aunque la respuesta completa tarde 15.

Observabilidad LLM: trazas y spans

No puedes optimizar lo que no mides. Primero instrumenta, después optimiza, nunca al revés.

Anatomía de una traza

  • Traza = un request de usuario, de punta a punta
  • Span = cada paso: retrieval, llamada LLM, tool call, parsing
  • Cada span lleva metadata: modelo, tokens in/out, costo, latencia, error

Herramientas

  • Langfuse: open source, self-host o cloud; decorador @observe en Python
  • Datadog LLM Observability: si tu empresa ya vive en Datadog, se integra al APM existente
  • Cualquiera sirve; lo que no sirve es no tener ninguna

Las métricas que importan

Métrica Qué responde Objetivo de ejemplo
Costo por request ¿Cuánto me cuesta servir a un usuario? < $0.01 USD promedio
p50 de latencia La experiencia típica < 3 s
p95 de latencia La experiencia de los que se van < 10 s
Tokens in / out El driver directo del costo Detectar prompts que crecen sin control
TTFT (time to first token) La latencia percibida con streaming < 1 s
Tasa de error 429 (rate limit), 529 (overloaded), timeouts < 1% con retry

Mide p95, no el promedio: el promedio esconde la cola, y la cola es donde viven los usuarios frustrados.

Instrumentación mínima viable

# Mide latencia y costo en CADA llamada: sin esto, vuelas a ciegas
import time, anthropic
import structlog  # pip install structlog

client = anthropic.Anthropic()
log = structlog.get_logger()
PRECIO_USD_MTOK = {"in": 3.00, "out": 15.00}  # claude-sonnet-4-6

pregunta = "¿Cuál es la política de reembolsos?"  # el input de tu usuario

t0 = time.perf_counter()
resp = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    messages=[{"role": "user", "content": pregunta}],
)
latencia_ms = (time.perf_counter() - t0) * 1000

u = resp.usage
costo = (u.input_tokens * PRECIO_USD_MTOK["in"]
         + u.output_tokens * PRECIO_USD_MTOK["out"]) / 1_000_000

log.info("llm_request", model=resp.model, ms=round(latencia_ms),
         tokens_in=u.input_tokens, tokens_out=u.output_tokens,
         usd=round(costo, 6), request_id=resp._request_id)
# request_id: id del request para soporte de Anthropic (lo viste en S03); el SDK lo expone como atributo _privado

Un log estructurado por request. Langfuse o Datadog hacen esto por ti con un decorador, pero entiende primero qué se mide y por qué.

Ya mides. Ahora, ¿qué palanca mueves?

Ya tienes los números en la mesa: costo por request, p95, TTFT. Optimizar no es probar todo: es elegir la palanca que mueve TU número.

Eje costo

Prompt caching, model routing y batch: pagas menos por el mismo trabajo. Se miden en tokens y precio por MTok.

Eje latencia percibida

Streaming: no cambia el costo ni la latencia total, cambia lo que el usuario siente mientras espera. Se mide en TTFT.

Prompt caching: qué cachear y cuánto ahorra

Los números (Sonnet 4.6)

  • Input normal: $3.00 / MTok
  • Escritura de cache: $3.75 / MTok (1.25×)
  • Lectura de cache: $0.30 / MTok (0.1×) → ~90% de ahorro
  • TTL: 5 min (se renueva con cada hit); 1h opcional a 2× escritura
  • Mínimo cacheable: ~2,048 tokens de prefijo
  • Break-even: desde el segundo request ya ganaste

Es un prefix match exacto

  • Cachea: system prompt grande, definiciones de tools, documentos de contexto, few-shot
  • Lo rompe (silenciosamente): datetime.now() en el system, UUIDs por request, json.dumps sin sort_keys, tools que cambian
  • Orden: estable primero, volátil al final. Un byte distinto invalida todo lo que sigue

Prompt caching en código

# El system prompt grande se escribe al cache una vez y se lee barato
from pathlib import Path
SYSTEM_PROMPT_GRANDE = Path("system.md").read_text()  # tu prompt, ≥2k tokens
resp = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    system=[{
        "type": "text",
        "text": SYSTEM_PROMPT_GRANDE,  # >2k tokens, sin timestamps
        "cache_control": {"type": "ephemeral"},  # TTL 5 min
    }],
    messages=[{"role": "user", "content": pregunta}],
)

# Verifica que el cache de verdad pega: esto va a tu dashboard
print(resp.usage.cache_creation_input_tokens)  # escrito (1.25x)
print(resp.usage.cache_read_input_tokens)      # leído (0.1x)
print(resp.usage.input_tokens)                 # sin cache (1x)

Si cache_read_input_tokens es 0 en requests repetidos, algo está rompiendo el prefijo. Diffea los bytes del prompt y encuentra al culpable.

Model routing: el modelo correcto por tarea

# Haiku 4.5: $1 / $5 por MTok; Sonnet 4.6: $3 / $15 por MTok (3x)
MODELOS = {
    "simple":   "claude-haiku-4-5",   # clasificar, extraer, formatear, FAQ
    "complejo": "claude-sonnet-4-6",  # razonamiento, código, agentes
}

def completar(tipo_tarea: str, prompt: str):
    return client.messages.create(
        model=MODELOS[tipo_tarea],
        max_tokens=1024,
        messages=[{"role": "user", "content": prompt}],
    )
  • Si el 70% de tu tráfico es simple, routearlo a Haiku recorta ~2/3 del costo de ese tráfico, y suele ser más rápido
  • Empieza con reglas estáticas por endpoint; un router aprendido (estilo RouteLLM) es la versión 2, no la 1
  • Valida con tus evals que el modelo pequeño no degrada calidad en esa tarea: el routing sin evals es fe, no ingeniería

Batch API: 50% de descuento para trabajo offline

El trato

  • −50% en input y output, sobre cualquier modelo
  • La mayoría termina en < 1 hora; máximo 24 h
  • Hasta 100,000 requests o 256 MB por batch
  • Compatible con prompt caching: los descuentos se apilan

Úsalo / no lo uses

  • Sí: evals nocturnas, clasificación masiva, enriquecimiento de datos, resúmenes de backlog
  • No: nada que un usuario esté esperando en pantalla
  • Regla: si nadie mira el spinner, va por batch

API: client.messages.batches.create(requests=[...]) → poll de processing_status → batches.results(batch_id). Cada request lleva un custom_id para reconciliar resultados.

Streaming: latencia percibida ≠ latencia total

# Una respuesta de 800 tokens tarda ~15 s completa.
# Con streaming, el primer token llega en menos de 1 s.
with client.messages.stream(
    model="claude-sonnet-4-6",
    max_tokens=2048,
    messages=[{"role": "user", "content": pregunta}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
    final = stream.get_final_message()  # usage completo al terminar

log.info("llm_stream", tokens_out=final.usage.output_tokens)
  • Streaming no reduce el costo ni la latencia total; reduce el abandono
  • Mide TTFT como métrica de primera clase, separada de la latencia total
  • Bonus: para outputs largos el SDK lo exige; sin streaming, timeouts

Manos al código · 30 min en pareja

Vamos a instrumentar un mini servicio de Q&A (el de la sesión pasada sirve) y a tomar decisiones con los datos:

  • 1. Wrapper observado (10 min). Envolver cada llamada al SDK: latencia, tokens, costo y cache hits en un log JSON por request
  • 2. Generar tráfico (5 min). Correr 20 requests con prompts variados (algunos repetidos para ver el cache pegar)
  • 3. Calcular p50 / p95 y costo total (10 min). Script de 15 líneas sobre los logs; nada de herramientas todavía
  • 4. Decidir la palanca (5 min). Con los números en la mesa: ¿qué recorta más aquí, caching, routing o streaming? Defiende tu respuesta con datos

Entregable del bloque: un JSON de métricas y una frase: "la palanca más barata para este servicio es ___ porque ___".
