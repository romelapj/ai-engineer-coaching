Sesión 01
Fundamentos de LLMs

Entender qué pasa por dentro de un LLM (tokens, atención, training, embeddings) para dejar de usarlo como caja negra.

Arrancamos con una pregunta tonta que casi ningún LLM respondía bien: ¿cuántas "r" tiene strawberry? La respuesta explica los tokens, la factura y la mitad de los bugs que vas a ver.

Objetivos de la sesión

Tokens y tokenización (BPE)

Entender cómo el texto se convierte en tokens y cómo eso impacta directamente tu factura.

Transformer y training

Explicar a alto nivel atención y capas, y distinguir pretraining de fine-tuning y RLHF.

Embeddings y similitud coseno

Representar texto como vectores y medir qué tan "cerca" están dos frases: la base de RAG.

Parámetros de muestreo

Dominar temperature, top_p y max_tokens: cuándo tocarlos y cuándo no.

Tokenización BPE: el modelo no ve letras

Cómo funciona BPE

  • Byte-Pair Encoding: parte de bytes y fusiona los pares más frecuentes hasta armar un vocabulario de ~32K–200K tokens.
  • Regla práctica en inglés: 1 token ≈ 4 caracteres ≈ 0.75 palabras. El español suele gastar más tokens por palabra.
  • Código, JSON y emojis tokenizan distinto al texto plano: mide, no asumas.

Por qué "strawberry" confunde

  • El modelo recibe straw + berry (2–3 fragmentos), nunca las 10 letras individuales.
  • Contar las "r" exige razonar sobre caracteres que el modelo literalmente no vio: por eso históricamente respondía "2".
  • Misma raíz de otros fallos: invertir strings, aritmética con dígitos largos, rimas exactas.

Lección: cuando un LLM falla en algo "trivial", pregúntate primero cómo se ve esa entrada en tokens.

Tokens = dinero: mide antes de llamar

# pip install anthropic: el endpoint count_tokens es gratis
import anthropic

client = anthropic.Anthropic()

count = client.messages.count_tokens(
    model="claude-sonnet-4-6",
    messages=[{"role": "user", "content": "¿Cuántas r tiene strawberry?"}],
)
print(count.input_tokens)  # conteo real, específico del modelo

# costo de input en Sonnet 4.6 ($3 por millón de tokens)
print(f"${count.input_tokens * 3 / 1_000_000:.6f}")

Ejemplo concreto: prompt de 1.000 tokens + respuesta de 500 en Sonnet 4.6 = $0.003 + $0.0075 = $0.0105 por request. A 100K requests/mes son $1,050. Nunca uses tiktoken para Claude: es el tokenizador de OpenAI y subestima ~15–20%.

Context window, pricing y elección de modelo

Modelo Context Max output Input $/M Output $/M Úsalo para
claude-opus-4-8 1M 128K $5.00 $25.00 Razonamiento duro, agentes de largo aliento
claude-sonnet-4-6 1M 64K $3.00 $15.00 Producción de alto volumen, mejor balance
claude-haiku-4-5 200K 64K $1.00 $5.00 Clasificación, routing, tareas simples y rápidas

El context window lo comparte todo: system prompt, historial, tools y la respuesta. En un chat, cada turno re-envía la conversación completa como input: el costo crece con el largo del historial, no solo con el último mensaje.

Muestreo: temperature, top_p, max_tokens

import anthropic

client = anthropic.Anthropic()
resp = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=300,        # tope DURO de salida; si lo toca, corta a media frase
    temperature=1.0,       # 0.0 = conservador · 1.0 = creativo (rango Claude: 0–1)
    messages=[{"role": "user", "content": "3 nombres para una fintech"}],
)
print(resp.stop_reason)  # "end_turn" ok · "max_tokens" = se quedó corto
print(resp.usage.input_tokens, resp.usage.output_tokens)  # lo que pagas
  • temperature escala la distribución antes de muestrear; top_p (nucleus) recorta a los tokens que acumulan p.ej. el 90% de probabilidad. En Claude 4+ usa uno u otro, nunca ambos: el API devuelve 400.
  • Receta: extracción/clasificación → temperature baja; brainstorming y copy → alta. Revisa siempre stop_reason antes de confiar en la salida.

El transformer en una slide

Ya sabes cuánto cuesta cada token y cómo controlar la salida. Abramos la caja: ¿por qué el modelo responde lo que responde?

  • Pipeline: texto → tokens → embeddings → N bloques (atención + feed-forward) → probabilidades del siguiente token → muestreo. Es autoregresivo: repite todo el ciclo por cada token que genera.
  • Atención: cada token calcula a qué tokens previos "mirar" y con qué peso. Así "banco" significa distinto en "me senté en el banco" vs "fui al banco a pagar": el contexto reescribe el significado en cada capa.
  • Capas: decenas de bloques apilados. Aproximación útil: las primeras capturan sintaxis local; las profundas, semántica y relaciones de largo alcance.
  • Lo que NO hay: ni base de datos de hechos, ni memoria entre requests, ni ejecución de lógica. Solo pesos congelados prediciendo el token más plausible.

De completador de texto a asistente

1. Pretraining

Predecir el siguiente token sobre billones de tokens de internet. Meses de GPU y millones de dólares. El resultado completa texto, pero no conversa: a "¿capital de Francia?" puede responder con más preguntas de examen.

2. Fine-tuning (SFT)

Se reentrena con pares (instrucción → respuesta ideal) escritos por humanos. Aquí aprende el formato asistente: responder la pregunta, seguir instrucciones, usar markdown.

3. RLHF

Humanos comparan respuestas A vs B → se entrena un reward model → el LLM se optimiza hacia lo preferido. De aquí salen el estilo, la utilidad y buena parte de la seguridad.

Implicación práctica: el "conocimiento" viene del pretraining (y se congela ahí); el "comportamiento" viene del post-training.

Limitaciones que tienes que diseñar alrededor

Alucinaciones

El modelo optimiza plausibilidad, no verdad: inventa con la misma confianza con la que acierta. Mitiga con grounding (RAG), citas verificables y permiso explícito para decir "no sé".

Knowledge cutoff

El pretraining congela el conocimiento en una fecha. Todo lo posterior no existe para el modelo, y peor: puede responder con datos viejos sin avisar. Mitiga con web search o tools.

No determinismo

Ni temperature=0 garantiza salidas idénticas (el cómputo en GPU por lotes no es determinista). Diseña tests tolerantes y usa structured outputs (lo veremos en la Sesión 03) cuando el formato importa.

Idea fuerza

Un LLM no consulta hechos: predice el siguiente token. El chat, el "razonamiento", las alucinaciones y la factura: todo es consecuencia de eso.

Si internalizas esta frase, el 80% del debugging con LLMs se vuelve obvio: casi siempre el problema está en qué tokens entraron, no en "que el modelo es tonto".

Embeddings y similitud coseno

Cambiamos de tema, no de herramienta: estos mismos vectores son la base de RAG (lo que construimos en la Fase 2) y los tocas hoy en el ejercicio.

  • Un embedding es un vector (p. ej. 1024 dims) donde la dirección codifica el significado: frases similares apuntan parecido.
  • Similitud coseno = coseno del ángulo entre vectores: 1 ≈ mismo significado, ~0 = sin relación. En código, dot / (norm·norm) es literalmente ese coseno del ángulo entre a y b.
  • Es la base de RAG, búsqueda semántica, deduplicación y clustering.
  • El API de Anthropic no expone embeddings: usa Voyage AI (su partner recomendado) o sentence-transformers open source. 
# pip install numpy voyageai
import numpy as np
import voyageai

def cos_sim(a, b):
    return np.dot(a, b) / (              # producto punto
        np.linalg.norm(a) * np.linalg.norm(b)  # longitud del vector
    )

# genera embeddings reales (necesita VOYAGE_API_KEY en el entorno)
vo = voyageai.Client()
textos = ["pagar con tarjeta", "checkout con visa", "receta de arepas"]
emb = vo.embed(textos, model="voyage-3.5").embeddings

print(cos_sim(emb[0], emb[1]))  # tarjeta vs visa   → ~0.83 (cercanas)
print(cos_sim(emb[0], emb[2]))  # tarjeta vs arepas → ~0.12 (nada que ver)

Manos al código: Token-ó-metro (30 min)

Construimos juntos un CLI en Python que responde la pregunta: "¿cuánto me va a costar esto, en cada modelo?"

  • Paso 1 (5 min): función que recibe un texto y lo pasa por client.messages.count_tokens() para claude-sonnet-4-6, claude-haiku-4-5 y claude-opus-4-8.
  • Paso 2 (10 min): tabla de pricing en un dict → calcular costo de input por modelo y proyección a 100K requests/mes.
  • Paso 3 (10 min): imprimir tabla comparativa y probar con 3 entradas: párrafo en español, JSON y código Python. ¿Cuál gasta más tokens por carácter?
  • Paso 4 (5 min): hacer una llamada real con messages.create() y comparar el estimado vs resp.usage. ¿Qué tan cerca quedamos?
  • Paso 5 (bonus): toma 2 frases del mismo tema y 1 de otro, genera sus embeddings (reutiliza el snippet de la slide "Embeddings y similitud coseno": voyageai o sentence-transformers) y calcula la cos_sim entre pares: comprueba que las del mismo tema puntúan más alto.
