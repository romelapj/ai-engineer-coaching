Desde hoy el juez es tu golden set: un puñado de casos con su salida esperada. Few-shot, CoT y XML se vuelven movimientos para subir ese score, no trucos sueltos.

Anatomía de un request

import anthropic

client = anthropic.Anthropic()

resp = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    # quién es el modelo y sus reglas
    system="Eres un analista de soporte. "
           "Responde solo en JSON válido.",
    # la conversación: turnos user/assistant
    messages=[
        {"role": "user",
         "content": "Clasifica: 'me cobraron doble'"},
    ],
)
print(resp.content[0].text)
  • system: rol, reglas y tono. Va aparte de los mensajes y pesa más que una instrucción suelta en el turno de user.
  • messages: turnos alternados user / assistant. Siempre termina en user.
  • max_tokens: techo de salida, no objetivo. Si la respuesta lo alcanza, se corta: revisa stop_reason == "max_tokens".
  • temperature: 0 para extracción/clasificación reproducible; sube solo para tareas creativas.

Este "analista de soporte" que clasifica reclamos es el caso que llevamos toda la sesión: de un request suelto a un clasificador medible.

Multi-turn: la API no tiene memoria

Cada request es independiente. El "chat" existe porque tú reenvías el historial completo en cada llamada, y pagas los tokens de todo el historial cada vez. 

history = [
    {"role": "user",
     "content": "Extrae el monto: 'pagué 45.000 COP'"},
    {"role": "assistant",
     "content": '{"amount": 45000, "currency": "COP"}'},
    # el turno previo del assistant también es contexto:
    # ancla el formato de las respuestas siguientes
    {"role": "user",
     "content": "Ahora: 'me cobraron veinte dólares'"},
]
resp = client.messages.create(
    model="claude-sonnet-4-6", max_tokens=256, messages=history,
)

Consecuencia práctica: una conversación de 20 turnos puede costar 10x más que el primer turno. Resume o recorta historial viejo cuando no aporte.

Streaming: latencia percibida vs real

with client.messages.stream(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    messages=[{
        "role": "user",
        "content": "Resume este hilo de soporte...",
    }],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)

# mensaje completo al final, si lo necesitas
final = stream.get_final_message()

Usa streaming cuando…

  • Hay un humano esperando: primer token en ~1 s en vez de 10–20 s por una respuesta larga.
  • La respuesta es extensa (resúmenes, redacción, código).

No lo necesitas cuando…

  • Es un pipeline batch: nadie mira la pantalla.
  • Necesitas la respuesta completa para parsear JSON: streaming no acelera el tiempo total, solo el primer token.

Nuestro clasificador de reclamos es justo ese caso: corre en batch y necesitamos el JSON completo para medir el score contra el golden set: ahí streaming solo suma complejidad.

Few-shot: los ejemplos mandan más que las instrucciones

  • 3–5 ejemplos suelen bastar. Más ejemplos = más tokens en cada request; mide si el sexto aporta.
  • Cubre los casos borde, no los fáciles. El modelo ya sabe clasificar "quiero mi reembolso". Dale el ambiguo: "el pago salió pero no llegó el producto".
  • Los ejemplos definen el formato de facto. Si tus 3 ejemplos responden en una línea, el modelo responderá en una línea aunque la instrucción diga otra cosa.
  • Balancea las clases. 4 ejemplos "fraude" y 1 "duplicado" sesgan la salida hacia fraude. 
system = """Clasifica reclamos en: fraude,
duplicado, no_recibido, otro.

<ejemplos>
<ejemplo>
texto: el pago salió dos veces el mismo día
clase: duplicado
</ejemplo>
<ejemplo>
texto: el pago salió pero nunca llegó el pedido
clase: no_recibido
</ejemplo>
<ejemplo>
texto: yo no hice esta compra
clase: fraude
</ejemplo>
</ejemplos>"""

Chain-of-thought: cuándo ayuda (y cuándo estorba)

Ayuda

  • Razonamiento multi-paso: cálculos, reglas encadenadas, decisiones con condiciones.
  • Extracción ambigua: "piensa en <razonamiento> antes de responder en <respuesta>" reduce errores en casos borde.
  • Debugging de prompts: el razonamiento visible te dice por qué falló, no solo que falló.

Estorba

  • Lookups y clasificación trivial: pagas 2–3x más tokens de salida y más latencia por la misma respuesta.
  • Cuando necesitas solo JSON: el razonamiento contamina la salida si no lo separas con tags y parseas solo <respuesta>.
  • Si el modelo ya acierta el 100% de tu golden set sin CoT, agregarlo es puro costo.

Regla práctica: empieza sin CoT, mide, y agrégalo solo si los fallos son de razonamiento (no de formato).

Estructura con XML tags

Los tags separan instrucciones, datos y formato. Eliminan la ambigüedad de "¿esto es parte del texto a procesar o una instrucción?", clave cuando el input viene de usuarios. 

texto_del_usuario = "me cobraron dos veces y nadie responde"

# en el bloque <formato>: {{ }} = llave literal en una f-string; el modelo recibe { }
prompt = f"""<instrucciones>
Extrae los campos del reclamo. Responde SOLO con el JSON,
sin texto adicional. Si un campo no aparece, usa null.
</instrucciones>

<reclamo>
{texto_del_usuario}
</reclamo>

<formato>
{{"tipo": "fraude|duplicado|no_recibido|otro",
  "monto": 0, "moneda": "COP", "urgente": false}}
</formato>"""

resp = client.messages.create(
    model="claude-sonnet-4-6", max_tokens=512,
    messages=[{"role": "user", "content": prompt}],
)

Bonus de seguridad: si el usuario escribe "ignora tus instrucciones", queda encerrado dentro de <reclamo>: es dato, no instrucción.

Prompts versionados en el repo

Un prompt en producción es código: vive en el repo, tiene diff, review y changelog. Nada de prompts editados a mano en un dashboard.

  • Un archivo por versión: el diff entre v2 y v3 te dice exactamente qué cambió cuando algo se rompa.
  • Cada versión lleva su score contra el golden set en el changelog: v2_few_shot · 17/20.
  • El código referencia una versión explícita. Rollback de prompt = cambiar una línea. 
prompts/
└── extractor/
    ├── v1_baseline.md      # 12/20 en golden set
    ├── v2_few_shot.md      # 17/20
    ├── v3_xml_tags.md      # 19/20
    └── CHANGELOG.md

# cargar el template en runtime
from pathlib import Path

PROMPT_VERSION = "v3_xml_tags"
template = Path(
    f"prompts/extractor/{PROMPT_VERSION}.md"
).read_text()
prompt = template.format(texto=texto_del_usuario)

Extracto de prompts/extractor/v3_xml_tags.md: {texto} es el único placeholder que rellena .format(texto=…); las llaves del JSON van dobladas {{ }} para que .format las deje literales (misma regla que la f-string de la slide anterior). 

<reclamo>
{texto}
</reclamo>

<formato>
{{"tipo": "fraude|duplicado|no_recibido|otro", "monto": 0, "urgente": false}}
</formato>

Errores comunes (los vas a cometer todos)

Error Síntoma Fix
Instrucciones contradictorias: "sé conciso" + "explica en detalle cada campo" Salida inconsistente entre runs idénticos Una sola regla por dimensión; si hay tensión, ordena la prioridad explícitamente
Contexto irrelevante: pegar el documento entero "por si acaso" Peor precisión, más costo y latencia: el modelo se distrae con lo que no importa Pasa solo las secciones relevantes; el contexto también se cura
Instrucciones críticas enterradas en el medio de un prompt largo El modelo "ignora" reglas que sí escribiste Reglas críticas al inicio del system prompt y repetidas al final si el prompt es largo
Pedir JSON sin definir el schema exacto Claves que cambian de nombre entre llamadas (amount vs monto) Muestra el JSON exacto esperado en <formato> y valida al parsear

La idea fuerza de hoy

Un prompt sin métrica es una opinión. Arma tu golden set primero, itera después.

El ciclo profesional: 1) escribe 10–20 casos con su salida esperada, 2) corre el prompt contra todos, 3) cambia una cosa, 4) vuelve a correr. Si el score no sube, revierte. Es el mismo loop de TDD que ya conoces: el prompt es la implementación y el golden set son los tests.

Manos al código: 30 min en pareja

Pair programming Clasificador de reclamos

Iterar un clasificador contra 10 casos etiquetados

  • Min 0–5: escribimos 10 reclamos de ejemplo con su clase esperada en golden.json.
  • Min 5–12: v1 baseline, instrucción simple + loop que corre los 10 casos e imprime el score.
  • Min 12–20: v2, XML tags + schema de salida explícito. Medimos de nuevo.
  • Min 20–28: v3, few-shot con los 2 casos que v2 falló. Medimos de nuevo.
  • Min 28–30: comparamos v1 vs v2 vs v3: ¿qué cambio movió más la aguja y cuánto costó en tokens?

Regla del bloque: ningún cambio de prompt sin volver a correr los 10 casos. Cero excepciones.
